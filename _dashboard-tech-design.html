1Goals & non-goals

Goals

  • One dashboard, index page lists every repo × pipeline combination that has ever reported results.
  • Drilling into a pipeline reuses Vally's existing charts, run history, and comparison views — unmodified.
  • Artifacts persist durably in Blob Storage so nothing is re-downloaded or lost on redeploy/restart.
  • New repos/pipelines appear automatically once they publish once — no code change to onboard.

Non-goals

  • Forking or reimplementing @microsoft/vally-server's API, schema, or UI.
  • Kusto, a data warehouse, or any ingestion pipeline beyond this app.
  • Building new charts — the existing Vally dashboard's charts are the ones we show.
  • Deleting add-result.ps1 / local dev workflow — kept for ad-hoc/manual use.

What "category" actually is today

categories.js hardcodes 4 entries ({slug, token, title, blurb}). A category page works by proxying the inner Vally dashboard's HTML and injecting a <script> that patches window.fetch so GET /api/runs only returns rows whose id string contains the token. There is no repo/pipeline column anywhere in Vally-server's own schema.

4Index page

Replaces the 4 static cards with cards computed from ingested data, grouped by repo:

SELECT repo, pipeline, COUNT(*) AS runs, MAX(ingested_at) AS last_run
FROM run_metadata
GROUP BY repo, pipeline
ORDER BY repo, pipeline;

Rendered as one section per repo, one card per pipeline within it, each linking to /p/<repo>/<pipeline>. A repo/pipeline appears the first time it successfully ingests — no code change needed to onboard a new one.

6Data model

Vally-server's schema is not forked. One small sidecar table, owned by this app, maps a run_id (Vally's own folder-name key) to the metadata it doesn't know about:

CREATE TABLE IF NOT EXISTS run_metadata (
  run_id      TEXT PRIMARY KEY,   -- matches vally-server's runs.id
  repo        TEXT NOT NULL,
  pipeline    TEXT NOT NULL,
  branch      TEXT,
  build_id    TEXT,
  build_url   TEXT,
  ingested_at TEXT NOT NULL
);

Populated from a small manifest.json sidecar file each CI pipeline uploads next to its results.jsonl:

{
  "schemaVersion": 1,
  "repo": "azure-rest-api-specs",
  "pipeline": "skill-eval",
  "branch": "main",
  "buildId": "20260825.3",
  "buildUrl": "https://dev.azure.com/azure-sdk/internal/_build/results?buildId=..."
}

Runs with no manifest (old local test runs) fall back to repo="unknown", pipeline=<folder name> so nothing breaks retroactively.

7Ingestion flow

  1. CI pipeline finishes its eval run, uploads results.jsonl + manifest.json to vally-runs/<repo>/<pipeline>/<run-id>/.
  2. The dashboard's sync loop lists the container, diffs blob run-ids against what's already in run_metadata, and downloads only the new ones into the local staging folder.
  3. Vally-server's own ingestDirectory() runs unmodified against the staging folder.
  4. For each newly-ingested run, the sync loop reads its manifest.json and upserts a row into run_metadata.
Known v1 tradeoff Listing the whole container on every poll is simplest and fine at current run volumes. If the container grows large enough for that to matter, a continuation-token-based incremental listing can be added later without changing the contract — not needed for v1.

10Rollout phases

  1. Data model & manifest contract — add lib/run-metadata.js, the sidecar table, manifest parsing, legacy fallback for existing runs.
  2. Blob ingestion — add lib/blob-sync.js + dependency; wire into server.js behind env vars; local fs.watch path keeps working side-by-side.
  3. UI — rename/rewrite to pipelines.js; data-driven index page; /p/:repo/:pipeline route.
  4. CI integration — add an "upload results + manifest.json to blob" step to azure-rest-api-specs' eval pipelines, then to language-repo pipelines as they onboard.
  5. Cutover — point the deployed App Service at the blob container; manual Kudu upload path remains available but is no longer required for CI-produced runs.

11Open questions — blocking implementation

1Storage account

Use an existing storage account/subscription, or provision a new one? Which subscription owns it?

2CI → Blob authentication

Managed identity / workload identity federation from the ADO pipeline, a SAS token in a variable group, or a connection string secret?

3Manifest contract completeness

Is {repo, pipeline, branch, buildId, buildUrl} sufficient, or do we also need e.g. tier/area for filtering?

4Legacy local results

Keep ingesting the local results/ folder indefinitely alongside blob, or is blob meant to fully replace it once live?
